# Release Plan Release Please

Reads release-please state at a commit, read-only. preflight checks that every package has the source tag of its manifest version; plan reports whether the commit merges a pending release pull request and, if so, every release with its tags, name and notes.

[actions-release-plan-release-please-v1.1.2](https://github.com/TimSchoenle/actions/releases/tag/actions-release-plan-release-please-v1.1.2) · JavaScript action (node24)
<!-- /docs:generated header -->

Two read-only checks for a release pipeline in which release-please owns versions and changelogs but not tags or
GitHub Releases (`skip-github-release: true`), and [`release/publish-build-commit`](../publish-build-commit) creates
those instead.

release-please finds a package's previous release through the commit its tag points at, then walks the default branch
back to that commit. A consumer tag on a build commit outside the default branch is never reached, and release-please
then proposes every commit within its search depth as unreleased. The pipeline therefore gives release-please its own
tags on the default branch, the source tags: each component carries a prefix (`src-actions-x`), release-please looks
for `src-actions-x-v1.2.3`, and consumers pin `actions-x-v1.2.3` on the build commit.

## Usage

### Gate release-please and plan the publish

```yaml
name: Release

on:
  push:
    branches: [main]

permissions: {}

jobs:
  # Fails before release-please runs when a package's source tag is missing, which would otherwise
  # make release-please propose every commit in the history as unreleased.
  preflight:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: TimSchoenle/actions/actions/release/plan-release-please@0b3967d3d992d12aa88da1f8facf412b162d5ab2 # tag=actions-release-plan-release-please-v1.1.2
        with:
          mode: preflight

  # release-please, with skip-github-release: true, needs: preflight

  plan:
    needs: preflight
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: read
    outputs:
      is-release: ${{ steps.plan.outputs.is-release }}
      pull-request: ${{ steps.plan.outputs.pull-request }}
    steps:
      - id: plan
        uses: TimSchoenle/actions/actions/release/plan-release-please@0b3967d3d992d12aa88da1f8facf412b162d5ab2 # tag=actions-release-plan-release-please-v1.1.2
        with:
          mode: plan
          release-pr-author-id: '248313786' # the release App's bot user
          consumer-tag-pattern: '^(actions|configs)-[a-z0-9-]+-v\d+\.\d+\.\d+$'

  # build, attest and publish run when needs.plan.outputs.is-release == 'true'. The publish job
  # re-runs plan mode itself, so the notes files it reads are its own.
```

## Behaviour

- **`preflight`** reads the configuration and manifest at `sha` and fails, listing every missing tag, unless each
  package's release-please tag exists. Run it before release-please: a missing source tag is exactly the case in which
  release-please proposes the whole history.
- **`plan`** finds the pull request `sha` merged (`GET /repos/{owner}/{repo}/commits/{sha}/pulls`): merged, into the
  default branch, with `sha` as its merge commit, carrying `pending-label`. With `release-pr-author-id`, a pending pull
  request from anyone else fails the step rather than being skipped. Its releases are the manifest entries that differ
  between the commit's first parent and the commit.
- **Tags and names follow release-please**: `<component><tag-separator>v<version>`, with `tag-separator`,
  `include-v-in-tag` and `include-component-in-tag` read per package and from the top level, and their release-please
  defaults otherwise. A package that includes its component in the tag must set `component`. The consumer tag is the
  release-please tag without `source-tag-prefix` and must match `consumer-tag-pattern`; the release name is
  `<component without prefix>: v<version>`.
- **Notes** are the section of the package's changelog (`changelog-path`, default `CHANGELOG.md`) under the first heading
  that names the version as a whole token, up to the next heading of the same level. A changelog without that section
  fails the step.
- Every read goes through the REST API at `sha`, so the job needs no checkout. Nothing is written.
