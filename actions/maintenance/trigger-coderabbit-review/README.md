# Maintenance Trigger-coderabbit-review

Posts a CodeRabbit review command on a pull request as a user account, for repositories CodeRabbit no longer reviews automatically. Skips drafts, closed pull requests, forks and bot authors, and refuses a token that is not a user token.

[actions-maintenance-trigger-coderabbit-review-v2.0.2](https://github.com/TimSchoenle/actions/releases/tag/actions-maintenance-trigger-coderabbit-review-v2.0.2) · JavaScript action (node24)
<!-- /docs:generated header -->

CodeRabbit does not review public repositories with fewer than 10 stars on its own. On every pull request it posts
"This repository does not receive automatic reviews because it has fewer than 10 stars." and reports its check as
skipped, whatever `reviews.auto_review` says in `.coderabbit.yaml`. It still answers the review command, but only from
a user. The same comment from `github-actions[bot]` or from a GitHub App gets no reply and starts no review. A
comment from the repository owner gets "Review triggered" within seconds.

This action posts `@coderabbitai <command>` as a user, `@coderabbitai review` with the default `command`, so reviews
start without anyone typing it.

## Usage

### Review after the Generate workflow (.github/workflows/coderabbit-review.yaml)

```yaml
name: CodeRabbit Review

# workflow_run, not pull_request_target: GitHub runs this file from the default branch, so a pull
# request cannot rewrite the job that receives the token, and nothing from the pull request is
# checked out or run. It follows the pull_request workflow that generates files, so CodeRabbit
# reviews the head after the generated files are committed. pr_url is left empty: the action reads
# the pull request from the event and skips it when its head has moved since.
on:
  workflow_run:
    workflows: [Generate]
    types: [completed]

# A newer push to the same branch supersedes a run that has not posted yet. The head repository is
# part of the group, so a fork branch with the same name cannot cancel a run of this repository.
concurrency:
  group: ${{ github.workflow }}-${{ github.event.workflow_run.head_repository.full_name }}-${{ github.event.workflow_run.head_branch }}
  cancel-in-progress: true

permissions: {}

jobs:
  trigger:
    name: Trigger CodeRabbit Review
    # Only a successful run on a branch of this repository. A failed run usually means a generated
    # patch is about to be committed, and the run on that commit asks instead. A fork's run is
    # skipped here, before the job enters the environment that holds the token.
    if: >-
      github.event.workflow_run.conclusion == 'success' &&
      github.event.workflow_run.event == 'pull_request' &&
      github.event.workflow_run.head_repository.full_name == github.repository
    runs-on: ubuntu-latest
    timeout-minutes: 10
    # An environment restricted to the default branch keeps the token out of every other workflow.
    environment:
      name: coderabbit
      deployment: false
    permissions: {}
    steps:
      - uses: TimSchoenle/actions/actions/maintenance/trigger-coderabbit-review@49acdef9979f343817ec2a85ddd25e5f34befc8b # tag=actions-maintenance-trigger-coderabbit-review-v2.0.2
        with:
          token: ${{ secrets.CODERABBIT_TRIGGER_TOKEN }}
```

<!-- /docs:generated usage -->

No `pull_request_target` workflow is needed, which GitHub blocks by default on public repositories. The example
follows `Generate`, the `pull_request` workflow that produces generated files and holds no secret. Any `pull_request`
workflow that runs on every pull request into the default branch can take its place.

Following the generator means CodeRabbit sees the final files. When `Generate` leaves a patch to commit, its run
fails, the job is skipped, and the commit starts the run that asks for the review. A run whose head has moved by the
time the job starts is skipped as `outdated`. A generator that keeps failing on the final head gets no automatic
review until it passes.

`CodeRabbit Review` is a `workflow_run` workflow: GitHub always runs its default-branch copy, so a pull request cannot
change the job that holds the token, and nothing from the pull request is checked out. With `pr_url` empty, the
action reads the pull request from the event of the run that finished, takes the one into `base_branch` (the default
branch when it is empty) whose head is the commit that run ran on, and skips it as `outdated` when its head has moved
since. Keep the `coderabbit` environment restricted to the default branch, so no workflow a pull request adds can read
the token.

Each push to the pull request runs `Generate` again and asks for an incremental review of the new commits, which is
what automatic review did. A draft is skipped. To have it reviewed when it is marked ready, add `ready_for_review` to
the `pull_request` types of the triggering workflow.

### The request workflow for the alternative

The alternative example follows `CodeRabbit Request` instead, a `pull_request` workflow that holds nothing and only
completes. It reviews each push as soon as it lands, without waiting for generated files:

```yaml
name: CodeRabbit Request

on:
  pull_request:
    types: [opened, reopened, ready_for_review, synchronize]

permissions: {}

jobs:
  request:
    name: Request A CodeRabbit Review
    runs-on: ubuntu-latest
    timeout-minutes: 5
    permissions: {}
    steps:
      - name: Record The Request
        run: echo "CodeRabbit Review runs when this run completes."
```

### Duplicates and old comments

Each command ends with a hidden marker naming the head commit it asked about, which CodeRabbit ignores. With
`skip_duplicates`, the action reads the latest 100 comments and reviews first and posts nothing when CodeRabbit already
submitted a review on the head commit, or when the token's account already asked about it. A re-run of the workflow
or a second `ready_for_review` therefore costs nothing. When CodeRabbit answered that request with "Action not
completed", for example because it was rate limited, the next run asks again. Only markers in comments by the token's
account count, so pasting one into a comment does not suppress a review. Two runs for the same head that start
within a second or two of each other can both read before either posts, which costs one extra command.

With `collapse_outdated`, the action then collapses as outdated its earlier commands and every CodeRabbit reply to a
review command, including replies to commands typed by hand. The pull request keeps one expanded command, and
CodeRabbit's answer to it. A comment that cannot be collapsed is reported as a warning; the command is already posted.

The job needs no `permissions`: the comment is posted with `token`, not `github.token`.

### The token

A fine-grained personal access token of the account that should appear as the author of the comment:

- **Resource owner:** the account that owns the repositories.
- **Repository access:** only the repositories that run this workflow.
- **Permissions:** Pull requests, read and write. Nothing else.

Store it as a secret of the `coderabbit` environment, `CODERABBIT_TRIGGER_TOKEN` in the example, and allow only the
default branch to deploy to that environment. A `workflow_run` job runs with the secrets of the base repository even
when a fork started the run, so forks are kept out by the job's `if`, which skips a run from another repository before
the job enters the environment, and by the action, which skips it again as `fork`. With `pr_url` set, `reject_forks`
does the same.

Before reading the pull request, the action calls `GET /user` with the token and fails unless the token authenticates
as an account of type `User`. `github.token` and app installation tokens cannot call that endpoint, so passing one
fails the step on every run instead of posting comments that CodeRabbit ignores. A token GitHub rejects with 401, which is what an expired fine-grained token gets, fails
with its own message, since it needs replacing rather than a different kind of token.

## What it refuses

The step fails without posting anything when:

- the token does not authenticate as a user account;
- `command` is anything other than `review` or `full review`. The comment body is built from it, so a value with a
  second line could otherwise post a second CodeRabbit command;
- `pr_url` does not contain `owner/repo/pull/<number>`, or is empty outside a `workflow_run` job;
- the event payload of a `workflow_run` job cannot be read, or carries no `workflow_run`;
- GitHub returns the pull request without an author or without its head or base repository. The fork and bot checks
  would otherwise pass by default.
